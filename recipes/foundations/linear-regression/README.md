# Linear regression, two ways

Least-squares regression on house prices, fit by gradient descent — once with `mx.grad`
and a hand-written update, once through `mlx.nn` and `mlx.optimizers`. Same data, same
loss, same optimizer, same learning rate. The only thing that changes is the level of
abstraction, which is the point.

## What it teaches

- **What `nn.Linear` and `mlx.optimizers` actually do for you.** The manual variant is
  about fifteen lines of training loop; the `nn` variant is about the same length but
  gets a bias term, parameter management and a one-line switch to Adam. Reading the two
  side by side is more informative than either alone.
- **`mx.value_and_grad` vs `nn.value_and_grad`.** The first differentiates a plain
  function of an array; the second knows how to differentiate with respect to a module's
  parameter tree.
- **Why MLX's laziness will ruin your benchmark if you let it.** A training loop that
  calls `.item()` every iteration measures host synchronisation, not compute. See
  Gotchas.
- **Why this model needs no intercept.** Standardising centres both `X` and `y`, so the
  least-squares intercept is zero — which is also why `nn.Linear`'s bias converges to
  approximately zero. `train_nn.py` prints it so you can check.
- **Scaling discipline.** The scalers are fit on the training split only, and every
  metric is reported in dollars after converting predictions back out of standardised
  space.

**Not covered here.** There is no closed-form / normal-equations solution in this
recipe, and therefore nothing about `mx.linalg`, QR vs Cholesky, or `float32`
conditioning. That material is worth a recipe of its own; this one is about the two
gradient-descent routes.

## Requirements

Apple silicon, macOS 14.0 or later, and a **native arm64** Python 3.10 or later. If
`pip` reports `No matching distribution found for mlx`, the environment is the problem,
not the pin — check it with:

```sh
python3 -VV                                          # must be 3.10+
python3 -c "import platform; print(platform.machine())"   # must print arm64
sw_vers -productVersion                              # must be 14.0+
```

An x86_64 Python running under Rosetta (common with older Homebrew or Miniconda
installs) will not resolve `mlx`. `mlx-data` is stricter still: it publishes
`macosx_14_0_arm64` wheels only.

## Running it

```sh
pip install -r requirements.txt
make all            # trains both variants, writes results.md
make bench          # both variants on both cpu and gpu
make predict        # price one house
make test           # correctness tests, no extra dependencies
```

## How it works

`data_pipeline.py` loads the CSV through `mlx.data`, shuffles with a seeded
permutation, splits 80/20, and standardises. Both training scripts import it, so they
see identical inputs and the two rows of `results.md` are genuinely comparable.

`train_manual.py` keeps a weight vector and applies `w ← w − lr · ∇w` itself:

```python
loss_and_grad = mx.value_and_grad(loss_fn)
for _ in range(num_iters):
    loss, grad = loss_and_grad(w)
    w = w - lr * grad
    mx.eval(w, loss)
```

`train_nn.py` hands the same job to a module and an optimizer:

```python
loss_and_grad = nn.value_and_grad(model, loss_fn)
for _ in range(num_iters):
    loss, grad = loss_and_grad(model, X, y)
    optimizer.update(model, grad)
    mx.eval(model.parameters(), optimizer.state, loss)
```

Both save a checkpoint and a run record; `make_results.py` turns the records into the
results table.

## Gotchas

**Benchmarking a lazy framework.** MLX builds a graph and evaluates it only when forced.
Two ways to get a meaningless number: stop the clock without calling `mx.eval`, which
times graph construction rather than compute; or call `.item()` inside the loop, which
forces a host sync every iteration so you measure synchronisation. This recipe calls
`mx.eval` on the parameters and the loss each step to keep the graph shallow, collects
the loss arrays, and only converts them to Python floats after the timer stops. There is
also an untimed warmup so kernel compilation is not charged to the first iteration.

**`mlx.data` returns bytes, not strings.** `stream_csv_reader` gives each field as a
uint8 buffer, so every value needs `value.tobytes().decode("utf-8")` before it can be
parsed. That is what `_number()` in `data_pipeline.py` is for. It is the main friction
in using `mlx.data` for small CSV work, and worth knowing before you reach for it.

**Standardise the target, then remember to undo it.** The models are fit against a
standardised `y`, so raw predictions come out in standard deviations, not dollars.
Scoring those against raw prices produces an enormous, meaningless error. `y_test` is
deliberately kept in dollars here and predictions are converted back before any metric
is computed.

**Divide-by-zero on constant columns.** A column with zero variance breaks
standardisation. `Standardizer.fit` substitutes a std of 1 for those.

## Configuration

Everything lives in [config.yaml](config.yaml).

| Key | Default | Meaning |
|---|---|---|
| `seed` | `0` | Seeds the shuffle and the weight initialisation |
| `data.train_split` | `0.8` | Fraction used for training |
| `data.shuffle` | `true` | Shuffle before splitting; the CSV is not in random order |
| `train.optimizer` | `sgd` | `sgd` in both variants; `adam` in the `nn` variant only |
| `train.learning_rate` | `0.01` | Same for both variants, so they stay comparable |
| `train.num_iters` | `1000` | Full-batch iterations |
| `train.warmup_iters` | `10` | Untimed iterations before the benchmark window |
| `predict.example` | — | The house priced by `make predict` |

## Data

`data/Housing.csv` — 546 sales from Windsor, Ontario, used in Anglin & Gençay (1996),
"Semiparametric estimation of a hedonic price function", *Journal of Applied
Econometrics* 11(6). The same data ships in R's `Ecdat` and `AER` packages. 17 KB, so
it is committed rather than downloaded; the binary columns arrive already encoded 0/1.

Eleven features (`lotsize`, `bedrooms`, `bathrms`, `stories`, `driveway`, `recroom`,
`fullbase`, `gashw`, `airco`, `garagepl`, `prefarea`) predict `price`.
